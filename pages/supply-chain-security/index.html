Supply Chain Security

Every time you run npm install, you're trusting thousands of strangers to not run malicious code on your machine. Today that trust got violated — again.

What Just Happened

On March 31, 2026, Axios — the HTTP library you've probably used in every project this term — was compromised. Two malicious versions were published to npm using a stolen maintainer token.

Here's the timeline:

  • An attacker stole a long-lived npm access token from the primary Axios maintainer
  • They published axios@1.14.1 and axios@0.30.4 — both containing a new dependency called plain-crypto-js
  • That dependency was never imported anywhere in the Axios source code. It existed for one reason: to run a postinstall script
  • The script downloaded a platform-specific RAT (remote access trojan) for macOS, Windows, or Linux — then deleted itself to cover its tracks
  • Socket detected the malicious package 6 minutes after publication

Axios has over 100 million weekly downloads. This is the third major npm supply chain attack in six months.

How npm install Can Attack You

You've run npm install hundreds of times by now. But do you know what it actually does beyond downloading packages?

Any npm package can define lifecycle scripts in its package.json. The most common one is postinstall — a command that runs automatically right after the package is downloaded. No prompt, no confirmation, no sandbox. It runs with your full user permissions.

Here's what a malicious package.json looks like:

JSON
123456
{
  "name": "plain-crypto-js",
  "version": "4.2.1",
  "scripts": {
    "postinstall": "node setup.js"
  }
}

That's it. That's the whole attack surface. When npm installs this package, it runs node setup.js — which can do literally anything your user account can do. Read files, open network connections, install backdoors, exfiltrate tokens.

And here's the thing that makes this really dangerous: transitive dependencies. You chose to install Axios. But npm also installs everything Axios depends on, and everything those packages depend on. A typical project has hundreds of transitive dependencies you never explicitly chose. Any one of them can run a postinstall script.

❓So why does this feature exist? Packages like esbuild, sharp, bcrypt, and prisma use postinstall to compile native binaries or download platform-specific assets. It's a legitimate feature that attackers exploit. Vite depends on esbuild, so yes — your CS52 projects use postinstall legitimately.

Protect Your Dev Machine

Ok, scary stuff. But this is fixable. Here's what to set up — it takes about 5 minutes and you only do it once.

Install Socket Firewall (sfw)

Socket is the company that caught the Axios attack in 6 minutes. They make a free tool called sfw (Socket Firewall) that acts as a security proxy between npm and the package registry. Every package gets checked against Socket's malware database before it reaches your machine.

🚀 Install it globally:

Terminal
npm i -g sfw

🚀 Add this alias to your ~/.zshrc so every npm command routes through Socket automatically:

bash
123
# Socket Firewall — npm supply chain protection
alias npm="sfw npm"
alias npx="sfw npx"

🚀 Reload your shell:

Terminal
source ~/.zshrc

That's it. No account, no API key, no config files. From now on, every npm install checks packages against Socket's database first. If it finds known malware, the install is blocked. If it detects something suspicious but unconfirmed, you get a warning.

sfw also works with yarn, pnpm, and even pip for Python projects. GitHub repo here.

Lock Your Dependencies

Your package-lock.json file records the exact version of every package (including transitive dependencies) that was installed. This matters because without it, npm install can quietly resolve to newer versions you never vetted — like, say, a freshly compromised axios@1.14.1.

Two rules:

🚀 Always commit package-lock.json to git. If it's in your .gitignore, remove it.

🚀 Use npm ci instead of npm install when cloning a repo or setting up CI. It installs exactly what's in the lockfile — no resolution, no surprises.

Terminal
# when you clone a project or set up CI:
npm ci

# NOT npm install — which can resolve newer (potentially compromised) versions

Advanced: Disable Lifecycle Scripts

For extra hardening, you can tell npm to never run postinstall scripts by default. This is the nuclear option — it blocks the attack vector entirely, but it also breaks packages that legitimately need it.

🚀 Set the global default in ~/.npmrc:

ini
1
ignore-scripts=true

🚀 Then in any project that needs lifecycle scripts (like your CS52 Vite projects), add a local .npmrc in the project root:

ini
1
ignore-scripts=false
This will break npm install for projects using esbuild (Vite), sharp, bcrypt, Puppeteer, or Prisma — because those packages need postinstall to download native binaries. That's why the per-project .npmrc override exists. If you're not sure, just use sfw — it gives you protection without breaking your build.

A Note on pnpm

Since version 10, pnpm blocks lifecycle scripts by default. Instead of trusting everything, it uses an explicit allowlist (pnpm.onlyBuiltDependencies in package.json) where you opt in to specific packages that need postinstall. This is the right model — secure by default, opt-in to trust.

We're not switching package managers mid-course, but if you're starting a new project or setting up something for DALI, pnpm is worth considering. Socket wrote a good overview of why this matters.

Protect Your Team Repos

The steps above protect your dev machine. For team projects — CS52 final projects, DALI apps, anything with shared repos — you also want automated scanning.

Dependabot — free, built into GitHub. It opens PRs when known vulnerabilities are found in your dependencies. 🚀 Enable it in your repo's Settings → Security → Dependabot. It won't catch zero-days like the Axios attack (those aren't in the CVE database yet), but it handles the long tail of known vulnerabilities.

Socket for GitHub — a GitHub App that scans PRs for suspicious dependency changes. It catches things Dependabot can't — like a new dependency that makes network calls from a postinstall script. Free tier gives you unlimited repos with 1,000 scans/month.

Review lockfile diffs — when a PR changes package-lock.json, actually look at what changed. A new transitive dependency appearing out of nowhere is a red flag.

If You Think You're Affected

If you ran npm install on a project that depends on Axios in the last 24 hours, here's how to check:

🚀 Check if the malicious package exists in your project:

Terminal
# check if the malicious dependency is present
npm ls plain-crypto-js

# also check the directory directly
ls node_modules/plain-crypto-js/ 2>/dev/null && echo "⚠️ FOUND" || echo "✅ Not found"

🚀 If found — or if you're not sure:

Delete node_modules and reinstall: rm -rf node_modules && npm ci
Clear your npm cache: npm cache clean --force
Update Axios to the latest clean version: npm install axios@latest
Check for the macOS RAT payload: ls /Library/Caches/com.apple.act.mond 2>/dev/null
Rotate any tokens or secrets that were on the machine — npm, GitHub, AWS, database credentials
If you find the RAT payload, wipe and reinstall the OS. Seriously.
